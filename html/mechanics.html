機制詳解

內部到底怎麼運作

這個核心裡跑著兩套刻意分離的回合系統：地城探索用最傳統精簡的 TurnEngine（加入序＝行動序、撞擊即攻擊），戰棋戰鬥用 ToME4 行動值的 ActionBar（速度累積、移動一次＋行動一次）。兩者不共用、不互相依賴——共用的只有 ECS／地圖／存讀檔基建。 改任何一邊之前，先確認自己站在哪個模組。

為什麼要分兩套 地城側 src/core/turn/ 是「教科書式回合制」的乾淨地基，能量／速度差刻意不加。戰棋側 src/core/tactics/ 才是行動值排程。把行動條加回 TurnEngine 是明確禁止的——它們是兩個平行世界。

地城 · 核心

TurnEngine：一輪怎麼跑

維護一條 actor 的 std::list<entt::entity>，順序＝加入序（hero 最先加入，故每回合最先行動）。begin_round() 後反覆 step(ctx) 直到 RoundDone。

1
≡

actor list ＝ 加入序

沒有先攻、沒有速度排序。誰先 add_actor 誰先動。remove_actor 安全處理 cursor，死亡才從名單移除。

2
◆

act_point 行動值

每 actor 本回合首次輪到時 ActPointComponent 重設為 1000，行動後歸 0。目前一回合一次，為未來依成本多次行動預留。

3
⏸

依操控者分派

看 ControllerComponent：Player 回 WaitingPlayer 暫停等 submit()；Self／Faction 立即 decide() 取動作並 resolve()。

概念內容
StepResultActed / WaitingPlayer / RoundDone
EngineCtxregistry& reg ＋ decide / resolve / trace 三個 callback。registry 不由引擎持有，保持引擎純粹可測。
list 維護add_actor（重複略過）/ remove_actor / contains / clear / order() / size()
Action{ ActionKind kind; int param; }，僅 Idle / Move / Wait。沒有 Attack、沒有技能／詠唱。Move 時 param 是方向編碼。
玩家阻塞 輪到 Player 操控者時 step() 回 WaitingPlayer 暫停（即阻塞等玩家），等 submit(e, action) 後才續跑。 多角色時依加入序逐一行動；Self／Faction 則立即解算，不暫停。

地城 · 結算

apply_action：一個動作變成什麼

apply_action() 把單一 Action 結算到世界並發出 ZoneEvent。沒有獨立攻擊指令——移動進入有 actor 的格子就是攻擊。actor_at() 查某格站著哪個 actor（撞擊判定與 NPC 尋路避讓共用，公開在標頭）。

動作 / 情況結果發出的事件
Move → 撞牆 / 出界停住不動BumpedWall
Move → 撞到 actor（致死）扣 CombatStatsComponent.attack 傷害，目標死亡ActorDied
Move → 撞到 actor（未死）扣傷害，目標存活BumpedActor
Move → 空格（踩到道具）移動，自動拾取 health_potion 回血ItemPickedUp
Move → 踩到下樓梯移動，觸發下樓ReachedStairDown
Wait / Idle消耗回合，不做事—
死亡由呼叫端統一移除 被殺的目標只發 ActorDied 事件、不在此 destroy，由呼叫端（ZoneWorld）統一從 registry 與 actor list 移除。 這避免了「被殺者在同一輪後續又被存取」的越界問題。

方向編碼在 move_dir.h：encode_dir(dx,dy) / decode_dir(p,dx,dy)，方向 0..8（八方向＋原地）。

地城 · 敵人 AI

decide_npc：NPC 怎麼決定下一步

回合引擎唯一使用的 NPC 決策函式是 src/core/turn/npc_ai.cpp 的 decide_npc(reg, map, self, target, rng, cfg)——純決策函式，回傳 Action， 唯一副作用是更新自己 NpcAiComponent 的警覺狀態；世界的改動仍交給 apply_action()。放在 core 所以能直接用 doctest（不用開 Godot）。

decide_npc 決策順序
NpcAiConfig{ sight_radius = 10, alert_memory = 6 } 1 更新警覺：LOS + sight_radius 內看得見目標 → 警覺 └ 看不見時 alert_memory 逐回合遞減，到期解除警覺 2 已警覺 且相鄰 ── 撞擊攻擊（不受 move_chance 閘門） 3 擲 move_chance 骰 ── 沒過就 Wait 4 已警覺 ── 追擊：大 delta 軸優先，受阻換另一軸 5 未警覺 ── 四方向隨機徘徊 # 全程避開牆與其他 actor（actor_at 判斷） # 舊的 decide_chase / npc_ai_system 都已刪除，只剩這一套
勝利條件與成長 走下第 5 層樓梯（get_win_floor()）即通關；每下一層英雄成長最大 HP／治療／攻擊， 否則怪物逐層變強、英雄不變，第 5 層起會數學上打不贏。

戰棋 · 平行系統

SRPG 戰棋戰鬥機制

以下全在 src/core/tactics/，與上面的地城 turn/ 平行、不共用、不互相依賴。 設計主軸是 ToME4 行動值模型：單位靠速度累積行動值出手，一個回合能移動一次＋行動一次，攻擊即結束回合，殲滅一方分勝負。 橋樑層是 TacticsBattle : Node，與 ZoneWorld 平行。

戰棋 · 排程

ActionBar：誰什麼時候出手

ToME4 行動值排程，常數 kCtToAct = 1000。速度快的單位累積得快、出手得勤。

▸

advance()：累積到達標

每 tick 對所有單位 TurnGaugeComponent.ct += TacticsUnitComponent.speed，第一個 ct >= 1000 者出手。 平手取 ct 高者；再平手取加入序在前者——確定性，不靠亂數。

−

consume()：不歸零，保留溢出

出手後 ct -= 1000（不是歸零）。溢出的部分保留下來，所以快角偶爾能連動兩次——這正是行動值模型的手感來源。

forecast(reg, n)：預告不動真身 前端的行動條 UI 要顯示「接下來 n 個出手順序」，靠 forecast() 在 ct 的複本上模擬 n 步， 不動真實 ct。純函式、可測、無副作用。

戰棋 · 移動

可達集：能走到哪些格子

compute_move_field() 從單位出發做四方向 BFS（每步花費固定為 1，等價 Dijkstra）， 算出移動範圍內每格的步數場。unit_at() 查某格站著哪個戰棋單位。

阻擋規則
牆 ── 不可通行 其他單位 ── 不能穿、也不能停在人身上 可達步數 ── 受 TacticsUnitComponent.move_range 上限 reachable_tiles() → 前端畫「可移動的藍格」 path_to(dst) → 沿 dist 場回溯路徑 # 只給前端做走路動畫；核心結算是瞬移

戰棋 · 結算

apply_tactics_action：一個指令變成什麼

結算一個 TacticsAction{ Wait, MoveTo, Attack }。它只驗證幾何合法性—— 可達／射程／是否敵隊——不管「這回合是否已移動過」，那是 Battle 子狀態的職責。回傳 bool。

指令驗證什麼發出的事件
MoveTo(dst)dst 在可達集內（可達性）Moved / 失敗 Rejected
Attack(target)在 attack_range 內、且屬敵隊（TeamComponent）Attacked（＋致死 UnitDied）
Wait——
死亡不在此 destroy 被殺死的單位只發 UnitDied，不在此處 destroy（避免迭代失效），由 Battle 統一從行動條移除並 destroy()。 事件型別：TacticsEvent{ Moved, Attacked, UnitDied, Rejected }，橋樑層讀取後翻成 Godot signal。

戰棋 · 敵人 AI

decide_tactics：戰棋 AI 怎麼選格

decide_tactics(reg, map, self, moved, acted)：純決策函式回傳 TacticsAction，與地城 decide_npc() 同一個模式。 射程內就攻擊最脆的目標，否則移動到「進得了射程、但不必貼身」的格子。

選格排序鍵（依序比較）
1 deficit = max(最近敵人距離 − attack_range, 0) 越小越好 └ 先求「進得了射程」 2 nearest = 到最近敵人的距離 越大越好 └ 關鍵第二鍵：進得了射程就別再靠近 少了它，遠程單位會走進近戰射程送死 3 steps = 走幾步 越小越好
為什麼第二鍵要「越大越好」 弓手 attack_range=3。若只看 deficit，射程內任何格都同分，AI 可能挑到緊貼敵人的格子，下一回合就被近戰單位打死。 第二鍵讓它在「還打得到」的前提下站得越遠越好——這一條就是遠程單位不送頭的關鍵。

戰棋 · 回合狀態機

Battle：一個單位的回合

Battle 是一場戰鬥的子狀態機，管的是單一單位這一回合的合法性閘門—— 這正是 apply_tactics_action 刻意不管的那一塊。

一個單位的回合
begin_next_turn() ── 行動條選出 current() 單位 │ ├─ 移動一次（可選） │ │ │ ▼ └─ 行動一次：攻擊 / 待機 └ 攻擊即結束回合 規則：可「移動後攻擊」，不可「攻擊後再移動」 run_ai_turn()：AI 打完 current() 整個回合（最多 3 步防卡死） winner()：殲滅一方分勝負；兩隊同歸於盡不判
死亡單位的清理 死亡單位由 Battle 從行動條移除並 destroy()——core 端 registry 已查不到， 前端 tactics_view.gd 靠 _seen_units 快照仍能在訊息列叫出死者名字。
