怎麼看程式

不會迷路的閱讀順序

這頁告訴你：整體架構長怎樣、唯一一條分層鐵律、程式其實是兩套刻意分離的系統、 每個資料夾負責什麼、哪幾個檔案是「真相層」，以及只有五分鐘該打開哪三個檔。

最重要的一條

分層鐵律：只有 gbind 認識 Godot

src/core/ 完全 godot-free——純 C++／EnTT，可單獨用 doctest 測，不開 Godot。 src/gbind/ 是唯一認識 Godot 的橋樑層，#include <godot_cpp/…> 只能出現在這裡。 核心邏輯不得 include 任何 Godot header——這是全專案的地基。

分層方向：只能由上往下依賴
godot_zone/ GDScript 前端 · 場景 / 輸入 / 畫面 │ 呼叫方法、接 signal ▼ src/gbind/ ◀── 唯一認識 Godot 的橋樑（ZoneWorld / TacticsBattle） │ #include <godot_cpp/…> 只能到這裡為止 ▼ src/core/ 純 C++ / EnTT · 完全 godot-free · 可單元測試
改動守則 要在核心加功能時，若你發現需要 #include <godot_cpp/…>，代表你站錯層了——那段邏輯該待在 src/gbind/， core 只回傳純資料。破壞這條，單元測試就跟著垮。

心智模型

它其實是兩套刻意分離的系統

同一顆核心裡跑著兩個平行、互不干涉的場景，共用 ECS／地圖／存讀檔基建，但回合驅動各自獨立、不共用、不互相依賴。開遊戲後由主選單擇一進入。改任何一邊之前，先確認自己在哪個模組。

⌘

地城探索

src/core/turn/ 的 TurnEngine——最傳統回合制：一條按加入序排的 actor 名單、撞擊攻擊、下第 5 層樓梯通關。橋樑是 ZoneWorld。

◈

SRPG 戰棋戰鬥

src/core/tactics/ 的 ActionBar／Battle——ToME4 行動值模型：行動條排程、移動一次＋行動一次的單位回合、殲滅分勝負。橋樑是 TacticsBattle。

為什麼分開 地城側 2026-06-21 重構後刻意收斂成「教科書式最簡回合制」，作為乾淨地基；戰棋側的行動值排程另開 src/core/tactics/， 不會加回 TurnEngine。兩者只是恰好共用 ECS／地圖／存讀檔，回合邏輯零共用。

大圖

它在整個 gamecore 的哪一層

gamecore 規畫成三層，由大到小。這個 repo 只做最底層——區域層（Area Layer），也就是「你實際站在一張地圖上探索或對戰」的那一層。

gamecore 三層架構
World Layer 世界／全域時間、大地圖 │ Region Layer 區域群、跨地圖移動 │ Area Layer ◀── 本 repo（gamecore-zone） 一張地圖 · ECS · FOV · 兩個平行場景 （地城 TurnEngine ／ 戰棋 Battle）
出身 本層是從 opennefia-cpp hard fork 出來的：保留了成熟的 ECS／FOV／戰鬥骨架， 但把 OpenNefia 特有的機制整套拿掉，換上自己最精簡的傳統回合制引擎，之後再平行長出 SRPG 戰棋。

檔案地圖

每個資料夾在幹嘛

整個專案被 git 追蹤的檔案不多，心智負擔低。核心分成 src/core/turn/（地城）與 src/core/tactics/（戰棋）兩塊。

真相層

哪些檔案是「設計的權威來源」

程式碼會變，但設計意圖與唯一真相來源集中在少數幾個檔。要理解「現在怎麼跑」與「為什麼這樣設計」：

檔案它回答什麼問題
workflows/common/code-map/CODE_MAP.md東西在哪：程式碼導航 index，「改 X 去哪」的第一站
src/core/turn/turn_engine.h地城真相：actor list、begin_round/step、Player 阻塞 vs Self 立即解算
src/core/turn/npc_ai.h地城真相：decide_npc()——回合引擎唯一 NPC 決策（LOS 警覺/追擊/徘徊）
src/core/tactics/battle.h戰棋真相：Battle 子回合狀態機（移動一次＋行動一次、攻擊即結束）
src/core/serialize/all_components.h存檔真相：可序列化元件的唯一清單，新增/刪除元件務必同步
workflows/specs/2026-07-10-srpg-tactics-battle-design.md戰棋設計記錄與範圍界線（§9 明列不在切片內的後續主題）
SESSION-LOG.md目前還沒收尾的活狀態、每個決策的理由（最快的上手入口）

資料怎麼流

一次玩家輸入發生了什麼

前端永遠不直接改世界，只「提交指令」，規則全在 C++。地城按一鍵＝英雄行動一次＋整輪 NPC；戰棋是平行的另一條資料流。

地城：一次「按 D 往右走」的資料流
[GDScript] map_view.gd 按下 D │ world.player_move(1, 0) # 若未在回合中先自動開一輪 ▼ [GDExtension] zone_world_gd.cpp（ZoneWorld） 輪到英雄（WaitingPlayer）→ submit(hero, Move) │ pump()：反覆 step() 跑完整輪 NPC ▼ [C++ core] turn_engine.cpp / apply_action.cpp / npc_ai.cpp 英雄 resolve → apply_action(Move 1,0) │ NPC 們 decide_npc() → apply_action 追擊 ▼ 撞牆？撞擊攻擊？拾取？下樓梯？ → 發 ZoneEvent │ pump 到「玩家等待 / 回合結束 / 換樓層」才停 ▼ [GDScript] drain_events → signal（hero_attacked / hero_hurt / npc_died / game_won…）→ 重畫地圖 + 更新 HUD/訊息列
戰棋是平行的另一條線 前端 tactics_view.gd 點格 → TacticsBattle.command_move/attack/wait() → core 的 Battle 結算 → 發 turn_started / unit_moved / unit_attacked / unit_died / battle_over signal → arena_view.gd 重畫。 與地城那條完全獨立，只是同一套 ECS／存讀檔基建。
關鍵設計 C++ 擁有規則、擁有時間；Godot 只負責「畫面 + 輸入 + 訊號」。 核心引擎不持有 registry，保持純粹可測。玩家阻塞＝輪到 Player 操控者時 step() 回 WaitingPlayer 暫停等 submit()，C++ 不空轉。
